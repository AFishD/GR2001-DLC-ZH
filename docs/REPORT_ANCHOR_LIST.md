## 0. 结论速览（TL;DR）

1. **布局 y 确实是引擎用 `CharHeight` 算出来的**：`RSFont::CharHeight` @ `0x21A440`
   = `cvt.w.s(fld[1] × style.f6)`（`fld[1]`=面头字高基数，`style.f6`=`font+0x20` 高度缩放）。
   ELF 里有 **19 个调用者**用它做竖向居中、底对齐、列表行距、折行行距；另外
   `fld[13]`（`def+0x24`）也是布局高度，被 `0x208F30` getter 读出后用于 320×240 文本居中。
2. **在已取得 dump 的战役/小队屏、以及训练截图里，CH 全都是 26（= EN 口径）**，不是“不同 widget 的
   CharHeight 不同”。战术/快速任务没有直接 dump，但训练列表行距 30=CH+4 与它们同族（见 §2.2）。
   CN 战役屏的实测 dump：新兵 y=289、老兵 y=327、精英 y=365、中央选择器 y=337、上下箭头 y=312/359、
   `难度` y=284、`战役` y=18、`接受/返回` y=419、`浏览` y=418，**CH 均为 26**。
3. **当前偏移的主因不是字体度量，而是锚点补丁自身的三件事**：
   - **(A) y 区间硬分档**：cave C（`40<=y<400` 再 `-3`）+ bottom 段（`y>=270` 再 `-3`）
     造成 **y=270 处 3px 跳变**、y=400 处 3px 反跳。训练列表 1–7 的实测行距就是
     **30,30,30,30,26.7,30 game px**——第 5→6 行正好少 3px，因为第 6 行 y 从 253.7 跨到 280.4。
   - **(B) cave D 按“字符串前 4 字节”匹配**：`老兵` 在难度列表行（y=327）和中央选择器（y=337）
     都命中 `+10`，而上下箭头不命中（净 `-1`）；于是同一屏里选择器比箭头低约 10px。
   - **(C) cave E 按 `y∈[235,345]` + 形如 `X. ` 的姓名匹配**：滚动/换屏后姓名行 y 一变就只命中一部分；
     probe40 的三行姓名 y=330/355/380，按当前窗口只有 y=330 那行能拿到 `+8`。
     A/B 组、以及同一组内不同行因此会差 8px。
4. **另一个被任务背景写反的事实**：当前 cave A 的公式是
   `dy=(CharHeight-16)/2`，即 **居中**锚定，**不是底对齐**（`build.py` `_cave_a_words` 第 191–192 行：
   `sub.s f1,f21,16` → `mul.s f1,f1,0.5`）。底对齐应为 `CH-16`（CH=26 时是 +10）。
   这正是后来必须用 cave D `+10`、cave E `+8` 手工补的原因：一个全局锚点无法同时满足
   居中/底对齐/顶对齐三种 widget。
5. **根治方案（推荐）**：保留 EN 的布局度量（`fld[1]=26/26/42`、`fld[13]=26/26/42`），
   - 把 DrawString 的整条锚点链换成 **“quad 高钉 16、顶锚”** 的最小 cave（`y1=y, y2=y+16`）；
   - 撤掉 cave A/C/D/E/bottom 的全部 dy；
   - 把 5 个“居中/底对齐”布局站点的 `boxH-CharHeight` 改成 `boxH-16`，让每个 widget 自己把
     16px 字形放进自己的对齐族（top 0 / center (boxH-16)/2 / bottom boxH-16）。
   行距、行 pitch 继续用 CH=26（=EN），所以**行位置与 EN 一致**；字形则按各行 widget 的对齐方式
   正确落位。训练/战术/快速任务/难度/小队都不再依赖 y 区间或字符串匹配。

> 一句话：**当前不是“字库度量把布局带偏了”，而是“EN 布局 + 全局居中锚点 + 按 y/字符串打补丁”
> 这套组合本身不自洽。** 度量已经基本是 EN 口径，问题在锚点算法。

## 1. 引擎侧证据：布局 y 到底从哪里来

### 1.1 `CharHeight` 的字段与公式（0x21A440）

反汇编（`DLC_SLUS_208.20.elf`，VA=file+0xFFF00）：

```
0x21A440  lbu  v0,0x24(a0)        # font+0x24 = style.b4（固定宽标志；本工程全 0）
0x21A454  beqz v0,0x21A464
0x21A460  lw   v0,0x10(s0)        # 固定宽分支：font+0x10
0x21A464  jal  0x21A4B0           # 取 face def
0x21A46C  mtc1 v0,f0
0x21A474  jal  0x21A4A0           # 取 font+0x20 = style.f6
0x21A47C  mul.s f0,f20,f0
0x21A480  cvt.w.s f0,f0
0x21A484  mfc1 v0,f0
```

- `0x21A4B0`：`lw v0,0x28(a0); jr ra; lw v0,0xC(v0)` → **`def+0x0C` = FONT.RES face 头 `fld[1]`**。
- `0x21A4A0`：`lwc1 f0,0x20(a0)` → **`font+0x20` = style `f6`**（FONT.RES 尾部样式记录里的高度缩放）。
- 因此：**`CharHeight = cvt.w.s( fld[1] × style.f6 )`**。
  EN：large/default `fld[1]=26`、huge `42`；当前合并 FONT.RES 已把 `fld[1]` 恢复成 26/26/42。
- `fld[1]` 在展开态 FONT.RES 的具体偏移（`work/analysis/dlc_font_res.bin`，7,466 B）：
  - large：`0x29`（face 头 `0x25` + 4）
  - default：`0x92C`
  - huge：`0x122C`

### 1.2 19 个竖向布局调用者（按功能分组）

`elf_probe.py callers --targets 0x21A440` 实测 19 个 `jal`，与 `docs/ANALYSIS_ELF.md` §12 的“19 个调用者”一致。
关键站点与公式（VA / 行为）：

| VA | 作用 | 公式（反汇编实测） |
|---|---|---|
| `0x1FCA30` | 文本 widget：居中对齐（mode 0xC） | `y = widget+0xD9 + (widget+0x44 − CH)/2` |
| `0x1FCA70` | 文本 widget：底对齐（mode 0x8） | `y = widget+0x44 − CH − widget+0xD9` |
| `0x1FCA14` | 文本 widget：其余（顶/常量） | `y += widget+0xD8` |
| `0x203768` | 另一文本 widget：居中 | 同 `(boxH−CH)/2 + offset` |
| `0x215FF4` | 字符表逐行 | `rowY += CH + 2`（每行） |
| `0x216254` | 列表控件逐行 | `rowY = base + i×(CH+2)`（10 行） |
| `0x21631C` | 列表控件第二段 | `9×(CH+2)` 的整块高度 |
| `0x2163A4` | 列表控件第三段 | `rowY = base + i×(CH+2)` |
| `0x216490` | 列表控件末段 | `rowY = base + i×(CH+4)` |
| `0x21BAA0` | 折行/行高辅助 | 用 CH 参与行数/行高 |
| `0x21C6A4` | 与 `0x1FCA30` 同构（ComputeDrawXY 族） | 居中 |
| `0x21C6E4` | 与 `0x1FCA70` 同构 | 底对齐 |
| `0x239BF4` | 320×240 文本居中 | `y = 310 − CH/2` |
| `0x2A0E34` | 简报/过场文本 | 用 `CH` 做半行偏移 |
| `0x2A367C` | 过场文本 | `447 − CH` 等 |
| `0x2A3898` | 过场文本阴影 | 阴影偏移 `0.5×CH / 1.5×CH` |
| `0x2AE480` | 折行正文 | `y += round(1.5×CH)` |
| `0x2AE5A4` | 折行正文（大行距） | `y += 2×CH` |
| `0x2AE738` | 折行正文 | `y += CH` |

**结论**：行 pitch 与行距确实是 CH 驱动的（至少 `0x216254/0x21631C/0x2163A4/0x216490/0x215FF4`
以及 `0x2AE480/0x2AE5A4/0x2AE738`）；但 **本次报障的列表里，CH 实测就是 26**，见 §2.1。

### 1.3 `fld[13]` 也是布局高度（docs R14 的说法需要修正）

`0x208F30` 是一个极短的 getter：

```
0x208F30  lw  v0,0x28(a0)   # face def
0x208F38  lw  v0,0x24(v0)   # def+0x24 = fld[13]
```

调用者：
- `0x208CE8` / `0x208D80`：`0x208F30` 的返回值参与 `(0x140 − fld13/2)`、`(0xF0 − …)` 的 320×240 居中；
- `0x21C160`：把 `fld[13]` 缓存到 widget+0xF8，供后续文本布局使用。

当前合并 FONT.RES 的 `fld[13]` 仍是 **26/26/42**，与 EN 相同，所以**现在没有造成差异**；
但若有人为了“16px 化”把 `fld[13]` 一并改成 16，320×240 的居中文本会整体上移 5px。
**结论：`fld[13]` 不能动。**

### 1.4 `font+0x18` 是“字距”，不是“行距”

任务背景里把 `font+0x18` 称作行距，这一点需要纠正：

- `0x2199A0`：`jr ra; lw v0,0x18(a0)`；
- DrawString 在 `0x219930–0x219948` 把它加到 **x**：
  `x += font+0x18`（每个字形之后，且 `font+0x24==0` 时）；
- `StringWidth`（`0x21A4C0`）尾部 `0x21A54C–0x21A558`：
  `width += (len−1) × font+0x18`。

所以 `font+0x18` 是**横向 letter spacing/tracking**，不参与任何 y 布局。
竖向行距来自 `CharHeight`（§1.1）与各调用者的 `CH+2/CH+4/2×CH`。

### 1.5 FT 记录高度只进 UV，不进布局

- `CharWidth`（`0x21A360`）只读记录 `+1`（advance）：
  `0x21A3C0 lbu 0x20(def)`（base char）、`0x21A3D4 lw 0x44(def)`（nrec）、
  `0x21A3E8 lw 0x38(def)`（记录表）、`0x21A404 lbu s0,1(v0)`（记录 +1 = advance）。
- `ComputeCharTextureCoords`（`0x21A210`）在 `0x21A244/0x21A290/0x21A2D4` 读记录
  `+2/+4/+6/+8` = `u0/v0/u1/v1`，仅用于纹理采样窗。
- 全 ELF 扫描 `def+0x38` 记录表读取点，未发现把 `v0/v1`（记录高度）用于 y 布局的消费者。

**结论**：我们把 FT 记录统一改成 16px，改变的是“采样窗高度”，不是布局 y。
布局 y 只受 `fld[1]×f6`（CharHeight）和 `fld[13]` 影响。

### 1.6 当前 FONT.RES 与 EN 的逐字段对比

用 `fontlib.ft_merge_for_dlc()`（= 当前 build 的数据口径）与 `work/analysis/dlc_font_res.bin` 对比：

| 字段 | 运行时地址 | 当前合并版 | EN 原盘 | 是否影响布局 y |
|---|---|---|---|---|
| large/default `fld[1]` | `def+0x0C`（`0x21A4B0` 实证） | **26 / 26** | 26 / 26 | **是**（CharHeight 基数；已恢复 EN） |
| huge `fld[1]` | `def+0x0C` | **42** | 42 | 是（已恢复 EN） |
| large/default `fld[2]` | 未逐项确认 | **32 / 32** | 26 / 26 | 静态未发现读取点；b4=0 时可能只是 fixed-width 备用值 |
| large/default `fld[3]` | 未逐项确认 | **32 / 32** | 26 / 26 | 同上 |
| `fld[4]×fld[5]` | → nrec（`font+0x44`） | 224 / 224 / 224 | 224 / 224 / 224 | 否（记录数） |
| `fld[12]` base char | `def+0x20`（`0x21A3C0` 实证） | 32 | 32 | 否（CharWidth 索引） |
| `fld[13]` | `def+0x24`（`0x208F30` 实证） | **26 / 26 / 42** | 26 / 26 / 42 | **是**（320×240 居中；已 EN，勿动） |
| style `f5` | `font+0x1C` | **全 1.0** | 0.6 / 0.8 / 1.2 / 1.63 / 1.64 … | 只影响 ASCII 宽度；中文 pair 不乘 f5 |
| style `f6` | `font+0x20` | **全 1.0** | #5=1.64 #6=0.8 #7=1.63 #8=0.8 #10=0.8 #12=1.2 #13=0.8 | **是**（CharHeight 缩放） |
| style `b4` | `font+0x24` | 全 0 | 全 0 | 否（固定宽早退不触发） |

- 当前 `fld[1]` 已经是 EN 值，`fld[13]` 也是 EN 值；**“恢复布局度量”这一步其实已经做过了**。
- 仍然不同的是 `fld[2]/[3]`（32 vs 26）和 style `f5/f6`（1.0 vs 原值）。
  `fld[2]/[3]` 未找到布局读取点；`f6` 的差异会造成**特定样式**的 CH 与 EN 不同：
  - #5：EN CH≈42，当前 26（Δ−16）
  - #6：EN CH≈33（huge 42×0.8），当前 42（Δ+9）
  - #7：EN CH≈68（huge 42×1.63），当前 42（Δ−26）
  - #8/#10/#13：EN CH≈20，当前 26（每行/每行距 +6）
  - #12：EN CH≈31，当前 26（Δ−5）
  但**本次实测的 5 类界面 CH 全是 26**，说明这些界面用的是 `f6=1.0` 的样式（#0–#4/#9/#11/#14 一类）。
  **所以 f6 是“下一批界面”的潜在风险，不是本次报障的根因。**

## 2. 本次报障的根因（带证据）

### 2.1 当前锚点链的实际算法与净位移表

按 `build.py` 的执行顺序（默认常量：`left=0, right_up=0, mid=3.0, bottom=3.0`）：

```
DrawString 非图标路径
  → cave A：dy = (CH−16)/2 = +5          （注意：居中，不是底对齐）
  → cave D：命中字符串 +10（新兵/老兵/精英）或 +4（B组）
  → cave E：未命中 D、且 y∈[235,345]、且形如 "X. " → +8
  → bottom：y>=270 → −3
  → cave C：40<=y<400 → −3
  → cave B：y1=y+dy, y2=y1+16
```

净位移（不含 D/E）：

| 输入 y 区间 | 净 dy |
|---|---|
| `y<40` | **+5** |
| `40<=y<270` | **+2** |
| `270<=y<400` | **−1** |
| `y>=400` | **+2**（cave C 在 400 处跳过） |

- **y=270 处向下跳 −3**（+2 → −1）；
- **y=400 处向上跳 +3**（−1 → +2）。

这就是“同一屏不同行落入不同区间”的直接来源。`cave C` 的 `40<=y<400` 与 bottom 的 `y>=270`
两个区间不是嵌套关系，而是**部分重叠**：`270..399` 同时吃到两份 −3。

> 注意：`tools/dlc/elf_patches.json` 里 bottom 段的 `why` 写的是
> “y>=400 且 x>400 再 -3.0”，这是 v9 的过期文案；**实际代码** `_bottom_words()` 用的是
> `y>=270`，且没有 x 条件。以 `build.py` 为准。

### 2.2 证据 1：训练列表 1–7 的实测行距在 270 处断掉

截图：`work/analysis/emu/scr42_training/scr_training_00.png`（v42，2100×1106；游戏 640×480，
等比放大 1106/480 = 2.304；横向 pillarbox）。在文字列 x=530..720 做亮度投影，七行 ink 中心：

| 行 | ink 中心（capture px） | 中心（game px） | 行距（game px） |
|---|---:|---:|---:|
| 训练1（选中） | 326.5 | 141.7 | — |
| 训练2 | 395.5 | 171.7 | 30.0 |
| 训练3 | 464.5 | 201.6 | 29.9 |
| 训练4 | 534.0 | 231.8 | 30.2 |
| 训练5 | 603.0 | 261.7 | 29.9 |
| 训练6 | 664.5 | **288.4** | **26.7** |
| 训练7 | 734.0 | 318.6 | 30.2 |

- 正常行距 = 30 game px = **CH(26)+4**，与 §1.2 的 `0x216490` 列表族一致；
- 第 5→6 行只有 **26.7**，正好少 **3.3px**；
- 训练5 的 y 参数（ink 中心减去 16px 格的 ink 偏置，约 8px）≈ **253.7 < 270**；
  训练6 ≈ **280.4 > 270**。
- 因此第 6 行开始吃到 bottom 段的额外 `−3`，与 `cave C` 的 `−3` 叠加；
  第 6/7 行相对第 1–5 行**整整高 3px**。这就是用户看到的“部分行靠上”。

如果列表有 8 行（快速任务 C01–C08）或 5 行（战术演习），它们只是跨越 270 的行号不同；
**只要行区间跨 270，就必然出现同一个 3px 断点**。这解释了为什么“训练/战术/快速任务”会一起报障。

### 2.3 证据 2：cave D 的字符串匹配把“老兵”选择器也一起下移了

`_CAVE_D_RULES` 只看绘制字符串的前 4 字节，不看 widget：

| 字符串 | 首 4 字节 | 额外 dy | 影响的所有出现位置 |
|---|---|---:|---|
| 新兵 | `B3A2E9A1` | +10 | 难度列表行（y=289） |
| 老兵 | `B3A2A2A5` | +10 | **难度列表行（y=327）** + **中央选择器（y=337）** |
| 精英 | `FEA3B7A2` | +10 | 难度列表行（y=365） |
| B组 | `0000C442` | +4 | B 组标题 |

probe33 的环形记录（`work/analysis/emu/anchor_probe33/ee_mem.bin`，记录 0–9、27–36）明确显示：
`老兵` 在 y=337（选择器）和 y=327（列表行）都被绘制，且前 4 字节都是 `B3A2A2A5`。
按当前净位移：

| 对象 | 输入 y | 净 dy | 最终 y1 |
|---|---:|---:|---:|
| 难度列表·新兵 | 289 | −1+10 = **+9** | 298 |
| 难度列表·老兵 | 327 | **+9** | 336 |
| 难度列表·精英 | 365 | **+9** | 374 |
| **中央选择器·老兵** | **337** | **+9** | **346** |
| 上箭头 `{` | 312 | **−1** | 311 |
| 下箭头 `}` | 359 | **−1** | 358 |
| `难度` 标题 | 284 | −1 | 283 |
| `战役` 标题 | 18 | +5 | 23 |
| `接受`/`返回` | 419 | +2 | 421 |
| `浏览` | 418 | +2 | 420 |

- 三个难度**列表行**的 +9 其实接近“底对齐”所需的 +10（误差 1px）；
- 但同一个字符串规则把**中央选择器**也推到了 346，而选择器本应居中（正确锚点 +5，即 342 左右）；
- 箭头只拿到 −1，于是选择器文本比箭头低约 **10px**。
  这就是“战役难度三项/选择器”看起来不齐的机制：**不是行高，是字符串规则命中了不同 widget。**

### 2.4 证据 3：cave E 的 y 窗口会让 A/B 组人名只命中一部分

`_cave_e_words()` 的条件：`235 <= y <= 345` 且 `(str[0..3]>>8)&0xFFFF == 0x202E`（形如 `X. `）。

probe40 的小队屏环形记录（`anchor_probe40/ee_mem.bin`，记录 29–40；ring 顺序不保证等于屏幕从上到下）：

| 姓名 | 输入 y | 当前 cave E 是否命中 | 净 dy（D 不命中） |
|---|---:|---|---:|
| C. Escobar | 330 | ✅（在 [235,345]） | −1+8 = **+7** |
| Eric Rogers | 355 | ❌（345<y） | **−1** |
| R. Perry | 380 | ❌（345<y） | **−1** |

- 三行 B 组姓名之间就会差 **8px**；
- 如果列表滚动、或 A/B 组整体上下移动，命中集合会变——**同一组行在不同滚动位置表现不同**；
- A 组姓名（S. Terry / P. Santiago / C. Corum）如果 y 落在 [235,345] 内会拿到 +8，否则不拿；
  这就是“A 组居中、B 组偏高/偏低”以及“同名行不同偏移”的机制。
- `开始` 按钮（probe40 y=365）不命中 D/E，净 **−1**；若它应居中/底对齐，就会比正确位置高 6–11px。
  这与用户报的“开始按钮”一致。

### 2.5 根因 D：全局“居中”锚点 vs 三类 widget 对齐

§1.2 的 19 个调用者里，至少有三类对齐语义：

| 对齐族 | 代表站点 | 公式（输入 y 是行盒顶） | 16px 字形正确锚点 |
|---|---|---|---|
| 居中 | `0x1FCA3C`、`0x203774`、`0x21C6B0` | `y = box + (boxH−CH)/2` | `dy = (CH−16)/2 = +5`（CH=26） |
| 底对齐 | `0x1FCA80`、`0x21C6F4` | `y = box + boxH − CH − off` | `dy = CH−16 = +10` |
| 顶对齐/常量 | `0x1FCA14` 默认分支 | `y = box + offset` | `dy = 0` |

一个全局 cave 只能选一个 `dy`：

- 选居中 `+5`：居中族正确；底对齐族高 5px；顶对齐族低 5px。
- 选底对齐 `+10`：底对齐族正确；居中族低 5px；顶对齐族低 10px。

当前选了 `+5`，所以：
- 居中族（训练/战术/快速任务的按钮行）基本正确，只被 270 分档破坏；
- 底对齐族（难度列表、开始按钮）需要 +10，作者用 cave D 的 +10 手工补；
- 顶对齐族被 +5 推低；
- 同一个 `+10` 又误伤了选择器（§2.3）。
**这是“按文本打补丁会越打越多”的结构性原因。**

### 2.6 为什么不是“字体度量把布局带偏”

- 已取得 dump 的战役/小队屏 CH 全 26（probe33/40），训练列表行距也对应 CH=26；等于 EN 的 `fld[1]=26`；
- 训练列表行距 30 = CH+4，与 EN 的 CH=26 同口径；
- 战役难度行距 38（289/327/365）与 CH 无关（或 CH+12），但输入 y 本身与 EN 同；
- `fld[1]`/`fld[13]`/`fld[12]` 都已是 EN 值；FT 记录高度不进布局（§1.5）；
- 所以**当前这批界面不可能仅由字体度量解释**。度量差异（`f6` 全 1.0）只会影响
  使用 #5/#6/#7/#8/#10/#12/#13 样式的**其他**界面，是下一批要排查的潜在项。

## 3. 根治方案

### 3.1 推荐：16px 顶锚 + 5 个“对齐站点”改成 16

#### 3.1.1 改动总览

1. **DrawString**：保留 `0x219894/0x219898` 两个 hook 站点，但把目标 cave 换成极小的
   “quad 高钉 16、顶锚”版本；撤掉 cave A/C/D/E/bottom 的所有 dy。
2. **布局站点**：把 5 条“居中/底对齐”公式里的 `CharHeight` 换成常量 16：
   - `0x1FCA3C`（居中）
   - `0x1FCA80`（底对齐）
   - `0x203774`（居中）
   - `0x21C6B0`（居中）
   - `0x21C6F4`（底对齐）
   这样每个 widget 用 **16px 文本盒**做自己的对齐；行 pitch / 行距继续用 CH=26，保持 EN 行位置。
3. **FONT.RES**：`fld[1]` 保持 26/26/42，`fld[13]` 保持 26/26/42；style `f5/f6` 暂保持 1.0。
   `fld[2]/[3]` 可留 32（未发现读取点），若要字节级 EN 对齐再单独评估。
4. **删除**：cave C（`0x182F84`）、cave B（`0x5752F0`）、cave A（`0x575D04`）、
   bottom（`0x59EF50`）、cave D（`0x57D1A8`）、cave E（`0x57D598`）的全部补丁表项。

#### 3.1.2 新的 DrawString cave（7 words / 28 B）

Hook 不变：

| VA | file | 原词 | 新词 | 说明 |
|---|---:|---|---|---|
| `0x219894` | `0x119994` | `E6970000`（`swc1 f23,0(s4)`） | `0815D741`（`j 0x575D04`） | 跳到新 cave |
| `0x219898` | `0x119998` | `E6C00000`（`swc1 f0,0(s6)`） | `00000000` | nop |

> `j` 编码：`(0x02<<26)|((VA>>2)&0x3FFFFFF)`；`0x575D04>>2 = 0x15D741`
> ⇒ `0x08000000|0x15D741 = 0x0815D741`。cave 末尾回 DrawString 的 `j 0x21989C` 是 `0x08086627`。

新 cave（VA `0x575D04`，file `0x475E04`，只用 28 B）：

```
0x575D04  3C084180  lui   t0,0x4180      # 16.0
0x575D08  44881000  mtc1  t0,f2
0x575D0C  4602B800  add.s f0,f23,f2      # y2 = y + 16
0x575D10  E6970000  swc1  f23,0(s4)      # y1 = y
0x575D14  E6C00000  swc1  f0,0(s6)       # y2
0x575D18  08086627  j     0x21989C
0x575D1C  00000000  nop
```

- `s4`/`s6` 仍是 DrawString 在 `0x219704/0x21970C` 设置的 `&rect.y0` / `&rect.y1` 指针；
- `f23` 仍是调用者传入的 y；
- 图标路径 `0x219850–0x21988C` 完全不动（图标仍按 CH=26 居中，20px，与 EN 一致）；
- 不带任何 dy，不再依赖 y 区间或字符串。

#### 3.1.3 5 个对齐站点的精确补丁

把 `subu v0, boxH, CH` 改成 `addiu v0, boxH, -16`：

| # | VA | file | 原词 | 新词 | 语义 |
|---|---|---|---:|---|---|
| 1 | `0x1FCA3C` | `0x0FCB3C` | `00621023`（`subu v0,v1,v0`） | `2462FFF0`（`addiu v0,v1,-16`） | 居中：`(boxH−16)/2` |
| 2 | `0x1FCA80` | `0x0FCB80` | `00821023`（`subu v0,a0,v0`） | `2482FFF0`（`addiu v0,a0,-16`） | 底对齐：`boxH−16−off` |
| 3 | `0x203774` | `0x103874` | `00621023` | `2462FFF0` | 居中 |
| 4 | `0x21C6B0` | `0x11C7B0` | `00621023` | `2462FFF0` | 居中（`0x1FCA30` 的同构副本） |
| 5 | `0x21C6F4` | `0x11C7F4` | `00821023` | `2482FFF0` | 底对齐（`0x1FCA70` 的同构副本） |

- 补丁后 `bgez/sra` 的“负数四舍五入”序列保持不变，仍能正确处理 `boxH<16` 的情况；
- 这 5 个站点覆盖了文本 widget 的居中和底对齐两支；顶/常量分支不动，天然正确；
- 行 pitch / 行距站点（`0x215FF4/0x216254/0x21631C/0x2163A4/0x216490/0x2AE480/0x2AE5A4/0x2AE738`）
  **不要改**，继续用 CH=26，保持 EN 行位置。

#### 3.1.4 为什么这套能同时满足五类界面

- **训练/战术/快速任务**：行位置由 CH+2/CH+4 决定，和 EN 一样；每行文本由自己的 widget
  以 16px 文本盒对齐（从截图看训练行是居中；若实际是底对齐，站点 2/5 同样覆盖）；
  不再有 270 分档，所以第 6 行不会突然高 3px。
- **战役难度**：三个列表行是底对齐族，站点 2/5 把它们按 `boxH−16` 底部对齐（= EN 的底锚点）；
  中央选择器如果是居中族，站点 1/3/4 让它居中；同一字符串不再共享偏移。
- **小队 A/B 人名**：姓名行按各自 widget 居中/底对齐；cave E 删除后不再受 `y∈[235,345]`
  和滚动位置影响，A/B 组、同组三行都一致。
- **开始按钮**：按它自己的 widget 对齐（居中或底对齐），不再被 y 分档推高 6px。
- **标题/底栏/简报**：标题按标题 widget 的对齐；底栏不再有 400 分档；简报正文行距保持 EN 26px。

### 3.2 对任务选项 (a) 的评估（“恢复 EN 布局度量 + 已有 cave 底对齐”）

**方向正确，但“只恢复度量 + 保留现有 cave”不足以根治**：

1. `fld[1]` 已经恢复成 EN（26/26/42），`fld[13]` 也是 EN；**这一步其实已经完成**。
2. 现有 cave A **不是底对齐，而是居中**（`(CH−16)/2`）。任务背景说“cave 负责底对齐”与代码不符。
3. 即使把 `fld[2]/[3]` 也恢复成 26，`CharHeight` 对这三类 widget 仍然是 26；全局 `+5` 仍然
   无法同时满足底对齐（+10）和顶对齐（0）。所以 **-3/-6 可以撤，但 per-widget 对齐还必须做**。
4. 若把 style `f6` 也恢复成 EN：
   - 好处：使用 #5/#6/#7/#8/#10/#12/#13 的界面，CH 与 EN 完全一致；
   - 代价：标题 #5 的 CH 变成 42、#7 变成 68（huge），16px 字形会被放进 42/68px 的行盒，
     除非这些 widget 也被站点 1–5 覆盖，否则会出现更大的空档/偏移；
   - `f5` 恢复会让 ASCII advance 变化，而中文 pair 的 CharWidth 恒 16（不乘 f5），
     中英混排步进比会重新变得不一致。
   **建议：不要整体恢复 f5/f6；只在证实某个界面确实使用非 1.0 样式且出现累计漂移时，单独评估该样式。**

### 3.3 备选方案（如果不想改 5 个布局站点）

- 保留 cave A 的居中 `+5`，撤掉 cave C/bottom/D/E；然后把两个底对齐站点改成 `boxH−21`
  （= `boxH−16−5`），让“布局 y + cave +5”仍落到 16px 底对齐。
  - 补丁：`0x1FCA80`/`0x21C6F4`：`subu v0,boxH,CH` → `addiu v0,boxH,-21`（`0x2462FFEB`/`0x2482FFEB`）。
  - 缺点：顶对齐族仍被 +5 推低 5px；需要再给顶部分支打补丁，最终仍是 5 个站点左右。
- 或**先只消跳变**：删掉 cave C 与 bottom 两段（保留 cave A 的 +5），净位移在所有 y 上统一为 +5；
  - 训练/战术/快速任务不再有 270 断点；底对齐族统一高 5px（需要站点 2/5 补），
    难度选择器也不再被 D 误伤（如果同时删 D/E）。
  - 这是“先验证根因”的最小改动，不是最终形态。

> ★ 注意：只把 cave C 的条件从 `40<=y<400` 改成 `40<=y` **不能**消掉 270 跳变：
> 270..399 仍然会吃到 C(−3)+bottom(−3)=−6。要消跳变，必须删掉/移走 bottom 的 `y>=270` 那 3px
> （例如把 bottom 阈值改成 400，或直接删 bottom），或者把 C/bottom 都删掉。

### 3.4 不推荐：把 `fld[1]` 改回 16（A′/A″ 路线）

- 布局行盒会缩小，按钮/面板若也读 CH 会整体变矮/上移（v7 已经踩过）；
- 所有 19 个调用者的 y 都会变，等于把“全局偏移”换成另一套全局偏移；
- 仍然需要 per-widget 对齐，且会牺牲 EN 的行位置。
**除非有完整 UI 回归，否则不要回到 `fld[1]=16`。**

## 8. 最终建议（给 Lead 的决策顺序）

1. **先做“消跳变”最小实验**（不动 FONT.RES）：删掉 cave C 与 bottom 两段（保留 cave A 的 +5），
   净位移在所有 y 上统一为 +5；观察训练 5→6 的 3px 是否消失。这能验证 §2.2 的根因，不涉及布局站点。
   > 只把 cave C 的 `40<=y<400` 改成 `40<=y` 是无效的（270..399 仍然 C+bottom 双重 −3）；
   > 必须删掉 bottom 的 `y>=270` 段或把它的阈值移到 400。
2. **再做“per-widget 对齐”正式修复**：按 §3.1 的 5 个站点 + 新 cave 一次改完，
   删除 cave D/E；用 §5.1/§5.2/§5.3 验收。
3. **最后再谈 style f6**：只有在其他界面出现“行距累计漂移”时，才按样式逐个恢复；
   不要为了“完整 EN”一次性把 f6 全改回去。
4. 如果时间只够做一件事：**删掉 cave C 与 bottom 两段 + 删掉 cave D/E**，
   至少能消掉 3px 跳变和“老兵选择器/姓名行”的字符串误伤；底对齐族会统一高 5px，
   但比现在“部分行高 3px、部分低 10px”更一致。
