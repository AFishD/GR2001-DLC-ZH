# 武器简介"多出单个换行"：机制、证据与最小修复

> 任务：静态确认武器说明面板是否被引擎自动折行、手写 `{br}` 与自动折行的相互作用，
> 给出宽度换算与最小改动方案。**未运行 PCSX2**；全部结论来自 ELF 反汇编、build 盘资源、
> 既有 EE RAM 转储与既有截图量测。
> 产物目录：`work/analysis/wrap2/`（本文件 + 脚本 + 候选 CSV + 中间输出）。

## 0. 结论速览

| # | 问题 | 结论 |
|---|---|---|
| 1 | DrawString/RSString 层会自动折行吗？ | **不会。** `DrawString`（`0x2195F0`）全程逐字节绘制，只特判 `0x20` 空格和两个图标码（v19 起为 `0x84/0x90`，原 `0xB5/0xB1`），**没有任何 0x0A/0x0D/换行分支**。 |
| 2 | 那自动折行在哪？ | 在**多行文本控件**的方法 `0x21B620`（类 vtable `0x5A7240`）。`SetText`=`0x21B560/0x21B5C0`，带标记的 `SetMarkupText`=`0x21AC90 → 0x21ADD0`（按 `{br}/{p}` 切段后逐段调 `0x21B620`）。 |
| 3 | 折行宽度由什么决定？ | `s7 = [widget+0x40] − [widget+0xB4]`（`0x21B690/0x21B698/0x21B6A0`）。**设计上**后面还有 cave M（`0x21B6AC → 0x59FFC4`）把 `s7` 钳到 ≤500；但实盘里 cave M 的 `slt` 编码可疑（见 §7），不要把它当可靠事实。字符记账 = `CharWidth(c) + font[+0x18]`（`0x21B79C/0x21B7A4`）；`font+0x18=1`（RAM 实测），即全宽字 17px、ASCII 9px。`StringWidth` 只用于"整段是否放得下"的预判（`0x21B72C`）和行尾余量（`0x21B844`），**不是折行上限**。 |
| 4 | 武器右面板的折行上限是多少？ | 可见金框仅 **263.9px（16.5 全宽字）**，但**引擎的 s7 明显更大**：v25 那版 19 全宽字的行（记账 327px）**没有被引擎二次折行**（截图实测），⇒ `s7 > 327`。上限要么是 `min(控件宽,500)`（若 cave M 生效），要么就是控件宽（若被跳过）；两者都 ≥328px ⇒ **≥19 全宽字**。同一 UI 家族里 4 个 w=245 的说明控件的行首向量是 25~26 字/行（425~442px），暗示"面板类文本框"的折行宽度约 **440px**。 |
| 5 | 手写 14 字 `{br}` 会被自动折行二次拆开吗？ | **不会**（14 字 = 238px < 327px ≤ s7）。武器说明的"多出单个换行"**不是自动+手动同时生效**。 |
| 6 | 那"多出单个换行"从哪来？ | **译文里残留的字面 `\r\n` 转义**（26/45 条武器说明）。注入时 `textlib.unesc_cell()` 把它反转义成真 CRLF，再由 `newlines_to_tags()` 变成**一个额外 `{br}`**；与手写 `{br}` 叠加就是 `{br}{br}`（空行），或在折行器把转义拆开时留下 1~2 字的孤行。盘上 T0016 实测有 **3 处 `{br}{br}`**、2 处单字行。45 条里合计 **59 个空行 + 41 个 <3 字短行**。 |
| 7 | M4 那种"缩短版 / 本。"也是这原因吗？ | 不是。那是 `wrap_sfxml` 以**单字**为 token、14 字断点正好落在"版/本"之间造成的**词内断行**；引擎上限更宽，不会纠正。 |
| 8 | 最小修复 | **纯数据**：① 清掉 T0016–T0060 的字面 `\r\n`；② 保留手写 `{br}`，按 14 全宽字重折（可用"词不拆/标点不落行首"）；③ **不要**改成"交给自动折行"；④ **不要**改控件宽度；⑤ 无需 ELF 补丁。候选表见 `translations_v43_candidate.csv`（251 行 / 0 空行 / 0 二次折行）。 |

## 1. 静态证据：换行发生在控件层，不在 DrawString

### 1.1 DrawString 不折行（`0x2195F0`）

```
0x21964C jal 0x2199F0          ; strlen
0x219750 addu v0,s2,s5         ; 串基址 + 字节游标
0x219754 lb   a1,0(v0)
0x219758 jal  wctomb           ; DBCS 补丁后进 decoder
0x219774 addiu v1,zero,0x20    ; ★ 空格特判
0x219778 beq  a1,v1,0x219914   ;   空格：只前进 x，不画
0x219794/0x2197A0 …            ; 图标码特判（v19 起 0x84/0x90）
0x21994C …（已改成 j 0x180918）; 游标步长
```
- 没有任何 `0x0A`/`0x0D` 比较；`{br}`/`{p}` 在运行时是 **4 个 ASCII 字符**（`'{'=0x7B` … `'}'=0x7D`），由控件层解析，根本不会传到 DrawString。
- 所以"引擎在 DrawString 层折行"这个假设可以排除。

### 1.2 自动折行 = 文本控件方法 `0x21B620`

类 vtable `0x5A7240`（次 vtable `0x5A72B0`，构造 `0x21B3xx`）。相关入口：

| 功能 | VA | 说明 |
|---|---|---|
| `SetText` | `0x21B560`（vtable+0x104） | 赋串到 `+0xA0`，若 `+0x108==0` 就调 `0x21B620` |
| `SetText2` | `0x21B5C0`（vtable+0x108） | 同上 |
| `SetMarkupText` | `0x21AC90` | 先赋串，再 `0x21ADD0` 解析标记 |
| 标记解析 | `0x21ADD0` | 扫 `{`(0x21AE10)/`}`(0x21AE20)，比较 `"br"`/`"p"`，**按段**调 `0x21B620` |
| `Wrap` | `0x21B620` | 真正的折行 |
| 行首向量 push | `0x21B9F0` | `[+0xAC]=数组, [+0xB0]=个数` |
| 行宽余量 | `0x21B888 → cave S 0x5880A4` | s4 小负不误判 |
| 行首 +1 | `0x21B8C4 → cave H 0x57B78C` | 断点是空格才 +1 |
| DBCS 解码 | `0x21B778 → cave A 0x5BFE0C` | 对偶码合并、步长 1/2 |
| 宽度补偿 | `0x21B7A0 → cave 0x5BFE84` | 对偶码少加一次 g |
| **行宽上限** | `0x21B6AC → cave M 0x59FFC4` | 设计意图 `s7=min(s7,500)`、`s4=s7`；实盘字节可疑，见 §7 |

**宽度来源（v42 ELF 实字节）**：

```
0x21B690  8EA30040  lw   v1, 0x40(s5)     ; s5 = this（文本控件）
0x21B698  92A200B4  lbu  v0, 0xB4(s5)     ; u8 内边距/余量
0x21B6A0  0062B823  subu s7, v1, v0       ; s7 = width - margin
0x21B6AC  08167FF1  j    0x0059FFC4        ; cave M
…
0x59FFC4  240801F4  addiu t0,zero,500
0x59FFC8  A901A000  slt   at,t0,s7
0x59FFCC  10200002  beq   at,zero,+2
0x59FFD0  00000000  nop
0x59FFD4  0100B82D  daddu s7,t0,zero
0x59FFD8  02E0A02D  daddu s4,s7,zero
0x59FFDC  AFA200CC  sw    v0,0xCC(sp)       ; 原 strlen 结果
0x59FFE0  08086DAC  j     0x0021B6B0
```

**每字宽度**：

```
0x21B78C  7FA200A0  sq   v0,0xA0(sp)    ; CharWidth(c)（DBCS 补丁后：全宽=16）
0x21B790  0C086668  jal  0x2199A0       ; font+0x18 → g
0x21B79C  00621821  addu v1,v1,v0       ; 单字成本 = CharWidth + g
0x21B7A4  0057082A  slt  at,v0,s7       ; acc + 成本 < s7 才收字
```
- `font+0x18` 在 RAM 里实测 **= 1**（`0x00BF2A20+0x18`，见 `scan_widgets_ram`/`font` 读取）。
  ⇒ 全宽字 = 17px/字，ASCII = 9px/字。
- `StringWidth` 只在这两处出现：整段预判（`0x21B72C`，若整段 < s7 就不折）与行尾余量（`0x21B844`）。**它不是折行宽度**。

### 1.3 `{p}` / `{br}` 的确切语义（`0x21ADD0`）

- 运行时标记是 ASCII 字面量：`"br"` 在 `0x587578`，`"p"` 在 `0x587580`（v42 ELF 实读 `b'br'` / `b'p'`）。
- 解析器对每个标记：把**标记前的文本**单独交给 `0x21B620` 折行，把产生的**所有行** push 进显示行向量 `+0x110`；然后从 `}` 之后继续。
  - `{br}`：只结束当前段 ⇒ **硬断行**；下一段另起一行。
  - `{p}`：额外 push 一个**空串**（`0x21AFEC/0x21AFF4 → RSString("") → 0x21B120`）⇒ **硬断行 + 一个空行**（EN 原设计里 `G058.I047` 开头就是 `{p}`）。
- **未知标记**（不是 br/p）走 `0x21B00C` 分支：直接 `substring(从 '}' 之后)`（`0x401EC0`），既不会把标记交给 DrawString，也不会先输出标记前的文本——**等于把标记连同它前面那段文字一起吞掉**。所以除 `{br}`/`{p}` 外不要写任何 `{...}`；`{{BTN:xxxx}}` 也不是这里处理（它在字符集编码层变成单字节图标码，见 `textlib.ICON_TOKEN_BYTES`）。
- **DrawString 不认 CR/LF**，因此盘上文本里不能靠真换行换行；必须用 `{br}/{p}`。

## 2. 武器右面板：宽度数值与换算

### 2.1 截图量测（v42，`work/analysis/emu/wc42/wc_weapon_attr_0.png`，640×480 口径）

| 项 | 数值 |
|---|---|
| 金框左右 | x = **325.5 … 589.4**，宽 **263.9px**（= 16.49 × 16px 字格；= 15.5 × 17px 记账） |
| 文字原点 | x = **335.5**（= 控件 x，见 2.2） |
| 最宽一行 ink | **235.2px**（右缘 570.7；离金框右内缘约 18px） |
| 行高/行距 | ink 高 ≈16px，行距 42px（含 16 字号） |

### 2.2 同布局控件实例（既有 EE RAM 转储，vtable `0x5A7240`）

`trace_probe18` / `anchor_probe*` 的 32MB `ee_mem.bin` 里能找到同类控件：

```
@010362F0 x=60  y=115 w=245 h=130 marg=0  text='代表士兵使用武器时的精准程度…'
@01036B80 x=335 y=115 w=245 h=130 marg=0  text='代表士兵承受身体伤害的能力…'
@01036DA0 x=335 y=268 w=245 h=130 marg=0  text='代表士兵提升身边所有士兵的能力…'
@00F41130 x=60  y=268 w=245 h=130 marg=0  text='代表士兵隐蔽移动的技巧…'
```
- `x=335` 与武器面板文字原点 **完全一致**，`h=130` 与面板高度 315/行距吻合；这组实例是同一套"右下说明框"模板。
- 若按 `+0x40=245` 算：`s7=245` ⇒ 14 全宽字/行（14×17=238 < 245 < 15×17=255）。**与当前手写 14 字吻合。**

### 2.3 但引擎对武器面板的**实际**折行上限更大（重要）

- v25 版 SFXML 武器说明是 **19 全宽字/行**（CSV 原文 `M4 卡宾枪是 M16 步枪的缩短版本。它发射{br}…`）。
  按 17px/字记账，这一行 = **327px**；v25 实机截图（`work/analysis/emu/weapon_capture/wc_weapon_attr_0.png`）里它**没有被引擎再折**，只是被面板右边裁掉。
  ⇒ 引擎接受该行 ⇒ **s7 > 327**，即 **≥19 全宽字**（若 cave M 生效则再 ≤29）。
- 4 个 w=245 的说明控件，其 `+0xAC` 行首向量是 **25~26 字/行**（425~442px）：
  ```
  widget 010362F0  line_starts=[0,50,56]  → 25 字 + 3 字（56 字节）
  widget 01036B80  line_starts=[0,53]     → 26 字（一行）
  widget 01036DA0  line_starts=[0,54,90]  → 27 字 + 18 字
  ```
  ⇒ 这些串在折行时的 `s7` 约为 **440px**，**不是当前的 245**。说明：
  1. "面板类文本框"在这套 UI 里存在 **≈440px** 的折行宽度；
  2. 折行用的是 **SetText 当时的宽度**，之后控件被布局改窄（245）**不会重折**（否则不会留下 425~442px 的行首向量）。
- 因无法排除"武器面板实例的 `+0x40` 也是 440/848"这一可能，**不能**把"引擎折行"当成可靠排版手段。

### 2.4 建议的手写行宽（units）

| 方案 | units | 引擎记账宽度 | 可见性 | 说明 |
|---|---|---|---|---|
| **推荐** | **14** | 全 CJK 238px / ASCII 混合 ≤244px | 右缘 ≈573，离框 16px | 与现版本一致，只是修数据 |
| 保守 | 13 | ≤221px | 右缘 ≈556 | 多留 16px，行数可能 +1 |
| 不可取 | 15 | 255px | 右缘 ≈590（贴框） | 若 `+0x40=245` 会被自动折；v31 实测已偏右 |
| 不可取 | ≥19 | ≥327px | 溢出/裁字 | 就是 v25 的问题 |

> `units` 口径：CJK/全角=1、ASCII=0.5。换算成引擎像素：**1 unit ≈ 16~17px**；14 units ≈ 224~238px。

## 3. "多出单个换行"的真实成因（按证据强度排序）

### A. 主因：译文里残留的字面 `\r\n` 转义（26/45 条）

**证据链**：

1. v34 译文表（构建 v42 用）的 CSV 单元格里是**四个字符** `\` `r` `\` `n`（不是真 CRLF；`count_escapes.py` 实测 0 个 0x0D/0x0A 字节）。
2. 注入时 `tools/dlc/inject_text.py:212` 调 `textlib.unesc_cell()` → **真 CRLF**；`:296` 再调 `newlines_to_tags()` → **一个 `{br}`**。
3. `tools/dlc/wrap_sfxml.py` 的 `rewrap()` **不清理**这种转义：`_tokens()` 把 `\r\n` 当成一个 2.0 units 的 ASCII token（`TOKEN_ASCII` 含 `\`、`r`、`n`），于是：
   - 若断点正好落在它前后 → 手写 `{br}` 与转义产生的 `{br}` **相邻** ⇒ `{br}{br}`（一个空行）；
   - 若折行器把它拆开 → 盘上出现 `{br}\r\n` / `\r{br}\n` 之类，反转义后变成 **2 个** `{br}`，或留下 1~2 字的孤行。
4. **盘上实证**（从 v42 ISO 解 EN_SPECIAL_FEATURE.XML，LZO 解压后按工程字符集解码；`dump_sfxml_v42.py`）：
   ```
   T0016: M18 定向反步兵地雷由曲面的{br}{br}方形硬质弹体制成，内装有{br}大{br}约340克C3炸药。
          {br}其{br}破片面由方形金属破片构成，{br}{br}起爆时破片以扇形射出。{br}{br}由于装药的原因，
          地雷在正{br}后方会{br}存在一小片杀伤区，{br}而爆炸正面{br}则是大范围的毁{br}伤区。
   T0017: M2爆破装药是一种定向聚能装药，{br}{br}能切穿混凝土及其他轻质建{br}材。…
   T0026: M4 卡宾枪是 M16 步枪的缩短版{br}本。它发射同样的 5.56 x 45mm{br}弹药，并使用同样的弹匣。   （无残留转义）
   ```
5. **量化**（`quantify_wrap.py`，45 条 T0016–T0060，按 17/9px 模拟）：

   | 指标 | v34/v42 现状 |
   |---|---|
   | 含字面 `\r\n` 的条目 | **26 / 45** |
   | 盘上 `{br}{br}`（空行） | **59 处 / 24 条** |
   | 引擎行数合计 | **417 行**（平均 9.3 行/条） |
   | <3 全宽字的孤行 | **41 行**（如「大」「其」「材。」「用。」） |

   ⇒ 右侧面板里看到「一句话中间突然多一行」「一个空行」就是这么来的。

### B. 词内断行（M4 的「缩短版 / 本。」）

- `wrap_sfxml` 以**单个 CJK 字符**为 token，14 字边界正好落在「版」「本」之间：
  `…步枪的缩短版{br}本。它发射同样的…`
- 引擎不会纠正（该面板上限 **≥19 字**），所以这行会一直显示成「…缩短版 / 本。…」。
- 这不是"自动+手动同时生效"，而是**手写断点落在词内**。同类还有 `45mm`、`M16A2` 等被拆（v42 的 token 化已经缓解）。

### C. ASCII 记账差（次要，本面板当前不会触发）

- 工具按 ASCII=0.5 unit=**8px** 记；引擎按 `CharWidth+g`=**9px** 记。
- 14 units 的纯 CJK 行 = 238px；14 units 全 ASCII（28 字符）= 252px。**只有当 s7 落到 245 附近时**，这种 ASCII 行才会被引擎再折一行。本面板实测 s7 > 327，所以不会触发；但若将来真的把控件改窄到 ~245，必须把工具改成 9px/ASCII，否则会重新出现"多一行"。

### D. `{p}` 的空行是**原设计**，不是 bug

- EN `G058.I047` 原文就是 `{p}Accuracy{br}…`；CN 译文保留了开头 `{p}`。实机「弹药…弹匣。」与「精准度」之间的空行在 EN 同样存在。
- 但如果用户看到的空行在**武器说明内部**（不是 I047 开头），那就是 A。

## 4. 最小改动方案（推荐 + 备选 + 风险）

### 方案 1（推荐，纯数据，2 个文件）

1. **清掉 T0016–T0060 的字面 `\r\n`**（这些条目的英文原文没有任何换行；转义是历史导入残留）。
   在 `wrap_sfxml.rewrap()` 开头加一行即可：
   ```python
   text = text.replace('\\r\\n', '').replace('\\r', '').replace('\\n', '')
   ```
   ⚠️ **只对 T0016–T0060 做**。T0063–T0098（特别收录/设计师日记）里也有大量 `\r\n`（47~353 处），它们是**另一界面**的排版断点，本次不动。
2. **保留手写 `{br}`，按 14 全宽字重折**；建议同时做：
   - 断点不落在常见二字词内（版本/弹药/装药/弹匣/系统/方形/炸药…）；
   - 收尾标点不落行首（若标点放不下，把前一个字一起带到下一行）。
   参考实现：`work/analysis/wrap2/fix_sfxml_wrap.py`（本目录，**不改 tools/**）。
3. 候选表：`work/analysis/wrap2/translations_v43_candidate.csv`（在 v34 基础上只改 T0016–T0060 的 40 条）。

   效果（同一模拟口径）：

   | 指标 | v34/v42 | 候选 |
   |---|---|---|
   | 行数 | 417 | **251** |
   | `{br}{br}` 空行 | 59 | **0** |
   | 引擎二次折行 | 12 | **0** |
   | <3 字孤行 | 41 | **5**（均为正常尾行，如「区。」） |
   | 最宽行 | 244px | **243px** |

   M4 变成：`M4 卡宾枪是 M16 步枪的缩短{br}版本。它发射同样的 5.56 x{br}45mm 弹药，并使用同样的弹匣。`
   （「版本」不再拆开；`5.56 x / 45mm` 仍跨行，属可再打磨的细节。）

### 方案 2（最小手工，工作量大）

只删 26 条的 `\r\n`（或把它们改成 `{br}`/直接删），不动折行。可消掉 59 个空行与大部分孤行，但保留 243px 的行和「版/本」这类词内断行。

### 方案 3（不推荐）"去掉手写 `{br}` 让自动折行负责"

- 该面板引擎上限 **>327px（≥19 字，最多 29 字）**，而可见框只有 **16.5 字** ⇒ 去掉手写断行会立刻回到 v25 的溢出/裁字状态。
- 引擎没有"词内不断"和"标点不落行首"规则，英文/数字 token 会被拆。
- 结论：**不可行**（除非同时把控件宽度改到 ~245）。

### 方案 4（不推荐）改控件宽度字段

- 需要先定位 UI 布局数据：**ELF 里没有**（`WTEXT/STEXT/KITWEAPON1…` 只是控件名注册表，`0x145E00` 一带；布局值不在 ELF），大概率在压缩的 `MENU.PAK` / `GR.IMG` 资源里（`MENU.PAK` 是 LZO 容器）。
- 即使改了：折行发生在 **SetText 当时**，事后改宽不会重折（RAM 里 w=245 的控件仍保留 425~442px 的行首向量就是证据）。
- 风险高、收益低，不建议本轮做。

## 7. 附带发现（需复核，不影响本次修复）：cave M 的 `slt` 编码可疑

`build.py` 的 cave M 源码意图是 `slt at, t0, s7`（若 500 < s7 就把 s7 设为 500），但生成的字是：

```
build.py:  (0x2A << 26) | (8 << 21) | (1 << 16) | (20 << 11)  = 0xA901A000
正确编码:  (8 << 21) | (23 << 16) | (1 << 11) | 0x2A          = 0x0117082A
```

v31/v36/v40/v42 四张盘上 cave M 的字节完全一致，capstone 反汇编为：

```
0x59FFC4  240801F4  addiu t0,zero,500
0x59FFC8  A901A000  swl   at,-0x6000(t0)   ← 不是 slt；地址 = 500-0x6000 = 0xFFFFA1F4
0x59FFCC  10200002  beqz  at,0x59FFD8
0x59FFD4  0100B82D  move  s7,t0
0x59FFD8  02E0A02D  move  s4,s7
```

即：① 每次 wrap 都会执行一条向 `0xFFFFA1F4` 的 `swl`；② "s7=500" 只在 `at != 0` 时生效（`at` 是 `0x402AB0`（RSString 长度）返回后遗留的临时寄存器值，不受控）。

- 但 wc42 / anchor 等实机 emulog 里**没有**对应的 TLB Miss（说明这条要么没真正落地、要么被 PCSX2 忽略/映射），且实机换行一直正常，所以**本次结论不依赖它**。
- 建议下一轮单独复核：在 `0x59FFC8` 下断点 / 读 `s7` 实际值；若确认编码错，应把该词改成 `0x0117082A`（并确认 `at` 由 `slt` 正确设置），否则"500 上限"与"29 字统一"的结论都只是巧合。
- 这属于 ELF 补丁质量项，与武器说明的"多出换行"**无关**，本轮不改。
